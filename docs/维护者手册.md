# 维护者手册

[English](maintainer-handbook.md) · [维护者](../MAINTAINERS.md)

这里放操作清单，不再复制一套发布实现。项目目前只有一名维护者；分支保护不等于独立人工复核，更不能为了让发布通过而绕过保护。

## 日常维护

- 遵循[协作流程](协作流程.md)，使用英文 Conventional Commits，让 `CHANGELOG.md` 的 Unreleased 部分对用户有用。
- 审阅分组依赖更新和[供应链检查](依赖与持续集成.md)。漏洞例外须有负责人、理由、准确版本和到期日；到期是复审期限，不是自动续期许可。
- 让文档、schema、示例、平台范围与真实测试一致。扩大支持范围前先留下实际结果。
- 普通问题走[支持渠道](../SUPPORT.md)，漏洞走[安全渠道](../SECURITY.md)。安全政策覆盖最新稳定版，不承诺无限回移补丁，也不单设开发版支持线。
- 不把未检查的流水、环境输出、模型目录或装配导出当成普通排障附件上传。

## 首次上线清单

以下是必须完成的动作，**不是已经完成上线的声明**：

1. 通过 `release/workflow-bootstrap` 把审阅后的配置合进 `main`，不用正式候选分支，不创建版本标签。
2. 回读 main/develop 保护：原生必需检查、基线必须最新、讨论须解决、管理员同样受保护、禁止强推和删除。默认分支已有对应任务之后，再扩充必需检查。
3. 允许 Actions 创建 PR，并开启仓库原生自动合并。默认 Actions 令牌保持只读，由各工作流声明具体权限。不添加个人令牌秘密来绕过事件限制。
4. 用管理员凭证启用不可变发布并回读确认；它约束未来发布。工作流令牌不能执行这项需要管理权限的预检。
5. 在 `main` 手动运行 **Synchronize development**，检查机器人 PR，必要时批准原生检查，确认同步通过保护完成。不要给正式发布候选启用自动合并。
6. 保持 `RELEASE_AUTOMATION_ENABLED` 未设置，明确发起 **Prepare release**，选择 `source=develop`。检查真实机器人候选、版本与变更记录，以及候选一致性验证。
7. 在该候选分支发起 **Release**，`expected_sha` 填准确提交。这只做签名预演。记录运行、候选分支与提交、各项检查和产物摘要。
8. 完成下面的取得、安装和版本切换演练，发现不符先修正，不把未做的提供方或兼容性测试算作通过。
9. 启用 `RELEASE_AUTOMATION_ENABLED=true`，回读设置和分支保护，把首个正式候选 PR 留给人合并批准，不为“完成设置”顺手发布。

## 预演验收记录

[签名预览验收记录](签名预览验收.md) 已记录一份固定候选的真实下载、来源与完整性验证及反向检查。本机安装和不同构建间的升级回退仍是独立的待验收工作。

在仓库留下经审阅的记录，写准确的运行编号、来源身份、摘要、命令与结果。不要把测试总数写成永久文档，它会漂移。

| 项目 | 应留下的证据 |
|---|---|
| 两平台包 | 真实托管 Linux/macOS 构建、署名资料生成、解包后的版本与帮助检查 |
| 签名分发包 | 四份文件对准确仓库、提交、分支、工作流的验证均成功 |
| 取得文件 | 下载真实的五文件预演产物，不用本地重建品代替 |
| 安装 | 专用 HOME 与项目目录，保留署名，检查实际程序路径和版本 |
| 无凭证启动 | 脚本或无界面检查，明确是确定性测试，不是真实模型 |
| 程序切换 | 保留旧预演或开发程序，暂存新程序，切换命令指针，再恢复旧指针 |
| 数据边界 | 只使用测试历史，把数据备份恢复与程序切换分开演练 |
| 真实提供方 | 明确执行过才单列记录，不从帮助、版本或脚本输出推导 |

目前没有两个正式版本可建立正式升级矩阵。开发或预演版本切换只证明流程，不证明任意跨版本存储兼容。不能改动正在承载维护者当前对话的运行时、模型凭证或真实历史。

### 可重复的运行检查

先单独验签并解开两个包，再运行 `python3.12 scripts/rehearse_runtime.py /absolute/old/lattice /absolute/new/lattice`。它不是安装器或验签器，不改传入的程序及署名文件；它另建临时 HOME、项目与套接字，不继承模型凭证。它检查四次独立启动：旧程序、新程序、旧程序读取较新的测试历史、旧程序读取升级前恢复的备份。报告核对文件名与内容，不宣称比较了所有文件系统元数据。

Node 检查器关联唯一输入、模型请求、成功结果、回复及同因的轮次结束。重启后的模型材料必须带上前一轮的**展开后输入**，只重放原始输入还不够。每次都必须确认启动、完成一轮新脚本回复并正常停机。CI 把同一程序传入两次来检验这套检查，`distinctBinaries: false` 明确表示**没有**验证跨构建升级。辅助程序结束时只清理自己创建的临时测试目录。

## 正常发布与热修复

依次参考[候选准备](发布准备.md)、[版本规则](版本与变更记录.md)、[产物说明](发布产物.md)、[发布与恢复](发布执行.md)。开发改动会刷新尚未合并的候选；把正式候选合进 main 就是发布批准。正常流程不要求另做手改版本、打标签和点发布的仪式，显式版本覆盖仍须审阅。

热修复先走经审阅的 `hotfix/*` → `main`，再从 main 准备独立的 `release/hotfix-next`。不要夹带尚未完成的 develop 工作。稳定历史经受保护的同步 PR 带回 develop。

## 工作流停下时

先看准确的失败任务，再考虑重跑。请求失败不代表远端未生效。不能强移标签、覆盖附件、绕过管理员保护合并，或伪造替代状态来遮住失败。

- 准备候选：检查既有 PR 和分支；未合并就关闭的候选需重新打开才恢复。
- 原生检查：通过 PR 修源码；到期依赖例外也必须先复审。
- 签名：检查事件提交是否等于构建提交，预演是否选了正确候选分支。检出代码不会改变 OIDC 来源身份。
- 上传草稿：保留原始签名分发包。同次运行可在 14 天内复用 `sealed-release-<commit>`，重新编译的不同字节不能代替它。
- 发布响应丢失：结果未知，先查再动；发布后的确认失败则意味着发布已经发生。
- 回同步：重跑同步任务，或在 main 发起恢复工作流。尊重人工 PR 和原生检查；冲突需要审阅，不自动解决。

没有自动删除或破坏性清理路径。不可变状态在发布后再核对；在那里失败属于需要调查的事故，不能当成从未发布。
