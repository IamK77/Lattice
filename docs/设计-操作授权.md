# 操作授权与界面临时权限

本文说明默认装配中的操作授权、界面临时权限，以及终端和 Ink 客户端的使用方式。它们是减少重复询问的机制，不是沙箱，也不是远程用户身份认证。

## 两种不同寿命的许可

**流内操作授权**回答“在这条流里，以后遇到同类操作是否还要问”。授权与撤销都记入流水，重开同一条流仍有效；另一条流不继承。撤销不回滚已经执行的操作，也不删除永久信任记录。

**界面临时权限**回答“这个实际发来工作输入的界面，现在是否允许免去询问”。一个界面实例只绑定一条流，一条流可以接多个界面；界面不等于终端窗口，也可以是机器人入口。服务把开启和关闭写成审计状态；退出会结束绑定，恢复历史不会恢复这项权限。整个运行时同时停机时，不承诺关闭快照已经先于停机落账，失效由运行寿命边界保证。永久信任和流内授权不会因为关闭界面开关而被删除。

旁观某条流并不参与授权。一个模型请求真正消费了多个界面的输入时，只要其中一个来源仍有临时权限，就可以免去询问；尚未消费的插话不能追溯批准已经发出的工具请求。最终答复结束旧工作，下一项工作不借用上一次说话人的权限。后台完成、定时器和监控沿创建它的调用追溯来源，而不是取最近说过话的人。跨流弱引用只用于导航，不用于继承授权。

## 怎样使用

在默认装配中，终端底部批准栏初始选中拒绝；用上下方向键在“仅本次允许”“本对话长期允许（重开保留）”和“拒绝”之间选择，Enter 确认。只有引入代码或指令的 trust 问题另有“永久信任（跨对话）”；强制逐次询问的操作不提供本流授权，没有新授权服务时也不显示不受支持的选项。`f` 本流授权、`p` 永久信任仍保留为快捷操作，Esc 始终拒绝。请求详情只在批准栏显示，PgUp/PgDn 翻阅完整内容，回答或请求结束后消失，不再作为长篇聊天记录显示；审计流水保留原文，旧历史重开也不会把授权请求重新画进聊天。终端和 Ink 均用 `Shift+Tab` 切换当前界面的临时权限：正常输入、模型忙碌或授权卡显示时都可用，不提交或清空草稿，也不批准当前卡。终端表单内仍保留“上一个字段”的导航；授权卡里的旧 `i` 键继续兼容。终端仅在临时权限开启时于底栏右侧显示红色 `permission`，关闭即隐藏；成功切换不再重复显示聊天记录和回执，失败原因仍显示，审计事件照常保留。Ink 在输入框为空时使用 `y` 仅本次、`f` 本流、`n` 拒绝、`p` 永久信任；已有输入时这些字母仍是正文。

两个界面均提供：

- `/permission`：查看**当前界面实例**的权威状态。
- `/permission on`、`/permission off`：请求开启或关闭临时权限。
- `/grants`：查看这条流已有的持久授权及其具体匹配范围。Rust 终端打开独立授权面板：上下键选择，PgUp/PgDn 翻阅完整范围，`d` 发起撤销、Enter 确认、Esc 取消确认或关闭面板，`r` 刷新。撤销请求发出后仍保留原行，等服务发布的新状态确认移除；读取失败与“没有授权”分别显示。Ink 暂保留文字清单。
- `/revoke <授权编号>`：撤销其中一项，不影响永久信任，也不撤销已经完成的操作。

请求发送成功不等于许可已经生效；开关和授权清单以服务发布的状态为准。切换临时权限不自动回答已经弹出的确认，当前卡仍需明确回答。组合命令会展示全部拟保存的范围；强制逐次询问的规则没有本流授权选项。

没有新授权服务的自定义装配或旧 daemon 不提供这些新控制。旧布尔批准保留原服务语义，尤其 trust 的旧批准仍会形成永久信任，不能把兼容路径标作“仅本次”。Ink 收到旧握手即清除新控件能力，不因自己发过能力声明就假定对端支持。

## 职责分开，内核不识别权限

- `effects-policy` 仍只按装配实例配置检查工具声明的读写、联网与执行作用面，不是按用户授权，也不是沙箱。
- `operation-policy` 匹配操作规则，提出确认，保存与撤销流内授权，并转交已有服务的授权答复。
- `interface-permissions` 保存当前界面的归属与开关状态，恢复时清空活权限。
- `trust-policy` 保留引入新代码、指令的确认与永久信任，同时接受适用的流内授权和界面临时权限。临时或流内批准不能写入永久信任。
- Browser、专家删除等服务保留自己的参数、版本、快照与执行校验；许可只替代适用的询问。
- 宿主负责界面身份和连接寿命；界面负责展示与收集决定。部件之间只读写可序列化事件，不共享一张可变的内存授权表。

内核仍只负责记账、投递、见证和调用结局，不增加“权限模式”的特殊分支。

默认请求链为专家预检 → 操作关卡 → 引入信任关卡 → 工具；前端的范围答复先交给操作关卡，再转交已有确认服务。两个关卡均可替换。声明要询问的装配必须有真实的前端答复路径，转交部件本身不算一个能回答的人。

内置专家使用独立装配，不继承主流的授权清单或界面开关。默认主流对未获准命令询问；无人值守的专家对仍需询问的命令返回拒绝，而不是永远等一张没人能回答的卡。不要把主流打开临时权限理解为替所有专家放行；专家需要的命令能力应由其独立装配明确配置。

## 命令匹配

命令规则匹配的是参数数组前缀，不是字符串子串。例如 `["git", "push", "origin"]` 可以覆盖同一远端的后续推送，但不覆盖 `upstream`，也不把 `push-other` 当作 `push`。多个规则同时命中时，禁止高于询问，询问高于允许；流内授权不盖过显式禁止或询问规则。界面临时权限可以跳过询问，但不能盖过禁止。

对于能够可靠解析的组合命令，逐条审查，全部许可后才将**原脚本完整交给执行方**。不会先执行已获准的一半。动态展开、重定向、循环等不支持的语法不作猜测，而是退回对完整 `bash -c` 请求的审查。

可持久化的建议由服务端生成，答复不能夹带一条更宽的新规则。裸解释器、包装器和没有明确远端的 `git push` 不自动获得宽前缀；这类请求只能保存原样参数授权。配置为必须询问的规则不提供一个实际上永远不会生效的流内允许选项。

**前缀不是执行隔离。** 它不约束后续参数、工作目录、远端名字对应的实际地址、PATH 指向的程序或脚本内容。整体参数授权也不是文件内容指纹。工具作用面的声明仍不是针对恶意部件的强安全边界。

解析器借鉴固定版本 Codex 的保守 Bash 解析方式；归属见根目录 `NOTICE` 和源文件说明。这里只复用了参数解析思路与对应实现，不引入 Codex 的沙箱策略或未命中规则的自动放行推断。

## 数据与恢复

模型请求通过 `workInputs` 指向本次工作实际消费的输入，工具续轮继续携带它，最终答复或等待状态结束它。取权限时不把整段历史材料当成来源，也不把授权答复的发送者算成原工作来源。没有来源标记的旧模型请求不猜测身份。回查错误不能当成“没有来源”。

界面服务发布 `interface.permission.state`，操作服务发布 `operation.authorization.state`。使用方按配置中的实例名读取权威快照。可以通过 `interfacePermissions` 和 `operationPolicy` 指定非默认实例名；改名必须同步配置相关使用方。界面控制命令只接受配置中的控制方，已经关闭的实例不能在当前运行寿命内重新启用。

宿主为每次新绑定分配新身份，不能让远程客户端自行冒认旧身份。默认身份生成器包含流标识、当前流水位置和进程内序号；断线、退出与重开不能把旧后台工作的身份重新赋给新界面。daemon 的关闭、断线和写出失败直接结束绑定，不等忙碌的模型轮次结束；迟到的订阅必须再核对绑定代次，不能重新打开已经离开的界面。为兼容旧调用方，解除订阅后仍可发送普通文字，但不再附带可用的界面权限来源。

权限服务崩溃、移除或主动报告不可恢复故障后，消费者停止使用它以前发布的临时权限。新运行期的开启记录也是失效边界：即使恢复时的空快照尚未落账，也不能读回上次的开启状态。这只处理已经进入流水的生命周期事实，不承诺识别尚未被宿主发现的死亡，也不能收回已经放行的操作。

操作确认使用独立的 `operation.authorization.answer` 通道，范围为 `scope=once` 或 `scope=flow`。新关卡先处理，再转成旧服务认识的答复通道；这样即使自定义装配保留 UI 到旧服务的直连，原始范围答复也不会抢先被旧服务执行或保存为永久信任。这个新通道必须明确给范围，不能省略后掉回旧语义。显式指定了错误类型或未知范围的答复不消费问题，也不降级成永久信任。为了兼容既有调用方，没有范围字段的旧布尔答复继续沿用原有服务语义；对 trust 而言那是原来的永久信任选择，界面不能把它标成“仅本次”。流内引入授权还保存当时声明的作用面，声明变化需要重新确认。

恢复只重建流内授权，不重放旧确认或执行操作。停止按同一调用的转发链判断；用户停止后才从上游送达的旧请求也必须结束为中断，新工作则不受之前的停止影响。撤销和停止都不是回滚。
