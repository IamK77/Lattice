# 发布执行

[English](release-publication.md) · [候选准备](release-preparation.zh-CN.md) · [产物说明](release-artifacts.zh-CN.md)

## 哪一步算批准

把正式候选分支 `release/next` 或 `release/hotfix-next` 的 PR 合进受保护的 `main`，就是发布批准。工作流重新检查实际合并提交、候选文件、版本历史和已有标签。部署工作流所用的引导 PR 不会触发发布；包注册表发布也不在本流程内。

维护者启用仓库变量 `RELEASE_AUTOMATION_ENABLED` 前，自动发布保持关闭。本文说明已经写出的机制，不表示正式版本已经发布。两种平台的构建已经单独实测；完整签名预演和正式启用仍须完成上线清单。

工作流事件对应的提交、检出的提交和获准构建的提交必须完全相同。GitHub 签名身份记录的是事件提交，不会随着后来检出的代码改变。因此，手动预演必须选择对应的候选分支，并把该分支的准确提交传给 `expected_sha`；不能从 `main` 发起，再要求它为另一个候选提交作来源证明。预演只接受对应候选分支或 `main`，正式发布只接受 `main`。

## 权限与顺序

1. 只读任务验证批准与来源。
2. Linux 和 macOS 各自在只读任务中编译、检查依赖、打包、解包并执行启动检查，不持有签名或发布权限。
3. 另一个任务把归档当作数据检查，生成两平台清单和校验和；这个任务不执行包内程序。
4. GitHub 为两个归档、`SHA256SUMS`、`release-manifest.json` 四份文件签署来源证明，保存可携带的证明文件 `provenance.json`。
5. 逐份验证仓库、准确提交、来源分支、签名工作流和签名任务的托管运行环境。
6. 正式分支先保存完整的五文件签名分发包，再占用不可挪动的 `vX.Y.Z` 标签、创建发布草稿、上传并核对全部文件，最后转为公开发布。公开后再核对不可变状态、标签和附件。

托管运行环境校验只证明**签名任务**的位置，不能单靠它推断之前所有构建任务的位置；构建任务的位置另由工作流固定。

预演任务只有仓库内容读权限，没有发布写权限，但会写入来源证明和 Actions 产物，因此不是“完全不产生远端写入”。它不创建标签或 GitHub Release。包内构建记录和分发清单都明确标记为预演；有签名也不等于正式版本。

## 验证来源

正式版本的四份受签文件分别运行：

```bash
gh attestation verify "$asset" --bundle provenance.json \
  --repo IamK77/Lattice --source-digest "$approved_commit" \
  --source-ref refs/heads/main \
  --signer-workflow IamK77/Lattice/.github/workflows/release.yml \
  --deny-self-hosted-runners
```

`--source-digest` 填准确的获准 Git 提交，不是归档摘要。预演要把来源分支换成实际候选分支。还要核对两个归档的校验和。只有校验和，或者未签名的 `BUILD-INFO.json`，都不能证明产物来自官方发布。获取和安装步骤另由安装指南负责。

## 中断与恢复

- 请求报错或响应丢失时，先查看标签和草稿；服务器可能已经接受操作。脚本不暗中重试，不删除、不替换、不挪标签。
- 已有附件必须名称、完成状态、大小和 SHA-256 都一致；一致便复用，不一致、重复、多出或尚未完成的附件一律停下。
- 在首次改变标签或草稿之前，工作流已经把完整签名分发包保存为本次运行的 `sealed-release-<commit>`，禁止覆盖。整次重跑和只重跑失败任务都会按运行、提交、产物编号和摘要寻找原包；找到后，整次重跑也不会重新编译。
- 原包保留 14 天。不承诺重新编译能得到逐字节相同的结果；原包过期或丢失时要调查，不能用覆盖上传、重新签署不同文件或强推标签来掩盖差异。
- 已上传的证明文件必须复用，不能换成一次新签名；新签名的字节本来就可能不同。
- 已经发布的版本直接下载原有不可变附件重新验证，不重建、不覆盖、不再次发布，之后的同步步骤可以独立恢复。
- 发布请求本身丢失响应，会明确报告“结果未知”；发布请求已经成功但后置检查失败，则明确报告“已经发布”。这两种情况都不能说成“什么也没发生”，也不自动回滚。

## 把稳定分支带回开发分支

发布成功后，独立任务把最新的受保护 `develop` 与 `main` 合入固定复用的 `hotfix/sync-main` 临时分支，再从它向 `develop` 创建或复用 PR，请求 GitHub 原生自动合并。临时分支满足“必须跟上目标分支”的保护要求，又不会把开发内容提前送入 `main`。发布产物的身份仍绑定原来的获准提交。不会直接写两条受保护分支，不会自动解决冲突、替换检查或绕过管理员保护。

同步分支只能积累受保护历史的无冲突 Git 合并。人工提交或改过内容的合并提交都会让任务停下，不自动保留或覆盖。任一受保护分支前进后，重跑同步即可更新同一条临时分支和 PR；中途失败可能留下已完成的合并，但只在临时分支上，任务会报错，不在内部重试。PR 合并后，确认尖端已进入 `develop`，再删除临时分支；下次同步重建同一个名字，不另开一条。

只为仓库机器人创建的同步 PR 请求自动合并，不接管人工 PR，也不改掉审阅说明。正式候选 PR 永远不获自动合并。正常的必需检查仍然生效；机器人触发的检查可能需要维护者先批准。请求失败时保留可见的 PR，并让任务报错。

首次引导或恢复时，在 `main` 上手动运行 **Synchronize development**。这在发布自动化未启用时也可用，且不会发布。`develop` 已包含 `main` 时，重复运行不产生写入。实测之前须允许仓库自动合并和 Actions 创建 PR。

## 启用前的仓库检查

管理员必须先启用不可变发布，并回读确认。Actions 的仓库令牌不能查询这项需要管理权限的设置，所以运行期检查的是已发布版本的 `immutable` 字段；发布后才发现设置未生效属于事故，不是可以撤回的预检失败。

启用自动化变量之前，先通过不发布的引导 PR 把工作流带进 `main`，完成真实签名预演，允许 Actions 创建 PR，确认分支检查与受保护的回同步，并确认没有意外发布首个版本。首个正式候选 PR 留给人来合并批准。
