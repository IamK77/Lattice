# 版本与变更记录

`Cargo.toml` 是 Rust 产品正式版本号的唯一正本。一次发布中的清单版本、锁文件里的本包版本、标签 `vX.Y.Z`、程序输出、发布说明和安装包名称必须一致。私有前端包的版本在准备发布时同步，但不发布到 npm。

## 构建身份

- 普通构建有 Git 信息时输出 `vX.Y.Z-dev+g<提交>`。
- 源码归档没有自己的 Git 仓库时输出 `vX.Y.Z-dev`。
- 发布构建设置 `LATTICE_RELEASE_VERSION=X.Y.Z`；如果与 Cargo 版本不一致，构建直接失败。对应程序输出 `vX.Y.Z`。

开发版本里的提交号只说明开发基线，不保证工作区干净；本地修改不一定反映在这个提交里。官方安装包靠构建来源证明与校验和识别，不能只相信版本字符串。仅使用 release 优化配置，也不等于官方发布。开发版本字符串会正确保留清单中已有的预发布标识与构建元数据。

## 提交与更新日志

提交使用英文 Conventional Commits，例如 `feat: ...`、`fix(cli): ...`、`docs: ...`、`ci: ...`、`build: ...`。不兼容变更用 `!` 或 `BREAKING CHANGE:` 标记，并说明迁移方法。不再要求自定义 `Type:` 尾注；历史尾注保留，但不再参与版本计算。

面向用户的变更记录在 [CHANGELOG.md](../CHANGELOG.md)。合并提交不重复计入变更，所以合并请求及合并提交可以按实际改动分类，不再一律要求 chore；准备发布本身使用 `chore(release): ...`。

发布候选会提出版本建议，并整理 Changelog 供审阅。已有发布线中，修复和性能纠正建议提升补丁版本，兼容的新功能建议提升次版本，不兼容变更建议提升主版本；1.0 以前，不兼容变更建议提升次版本。只有文档或维护改动时，不必发布新二进制。首版使用 `Cargo.toml` 已选定的版本。

维护者合并发布 PR 到 `main`，才确认这一版的时机和范围。准备不等于发布；不得编造历史版本、悄悄移动已经发布的标签，或把源码提交数量当作发布版本。
