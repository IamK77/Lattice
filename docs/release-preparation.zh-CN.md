# 准备发布

[English](release-preparation.md) · [版本规则](versioning.zh-CN.md)

准备只提出候选，不创建标签、不发布 GitHub Release，也不上传到包仓库。自动化默认关闭。
发布流水线通过演练之前，不设置仓库变量 `RELEASE_AUTOMATION_ENABLED`。启用该变量由维护者操作，不能代替审阅发布 PR。
自动化关闭时，仍允许维护者明确发起 **Prepare release**，以创建首个审阅候选并完成[签名预演](release-publication.zh-CN.md)。它仍然不能发布；上线步骤完成前不要合并候选。

## 正常路径

1. 按受保护分支流程，把已审阅的改动合入 `develop`。
2. 启用自动化后，**Prepare release** 从那个确定的来源提交计算候选，创建或更新面向 `main` 的 `release/next` PR。
3. 审阅版本、变更记录、兼容性与迁移说明以及 CI。GitHub 可能要求先批准仓库机器人创建的 PR 运行检查。
4. 准备发布时才合并该 PR，绝不为它启用自动合并。获批合并提交的标签和产物由发布流水线负责，不由准备脚本负责。

工作流需要仓库允许 Actions 创建 PR。它只使用短期仓库令牌，授予内容与 PR 写权限，不把个人访问令牌存为秘密。
它不直接写入 `main` 或 `develop`，不强推，也不绕过必需检查。

## 版本与变更记录

自动准备只支持稳定版 `X.Y.Z`。预发布渠道需要另行明确规则；开发构建标识仍然受支持。
首个候选采用 Cargo 已选定的版本。已有正式发布后，`feat` 建议增加次版本，`fix`、`perf`、`revert` 建议增加修订号，不兼容改动建议增加主版本（1.0 之前增加次版本），取其中幅度最大的一级。
只有维护性改动时，不要求发布新二进制。

要覆盖建议版本，通过正常审阅 PR 修改来源分支的 Cargo 包版本，必须高于上一个已发布稳定版。
在 `CHANGELOG.md` 的 `## [Unreleased]` 下提供可审阅的说明；只改版本号，不会凭空替维护性发布生成说明。

准备脚本同步 Cargo、锁文件中的本地包条目、私有前端包及其锁文件和 Changelog，保留已锁定的依赖版本。
人工整理的说明与历史章节会保留，面向用户的非合并提交补充到候选说明中。
生成的 `.release-candidate.json` 记录来源、上一份发布和候选版本。这是审计记录，不是批准凭证。

## 更新、中断与人工修改

- 同一来源重复准备，不重复产生候选提交。更新保留祖先关系，只做快进，包括分支已建立但 PR 创建失败后的恢复。
- 候选中的代码或生成文件被人工修改后，自动更新停止，不覆盖这些改动。把预期改动放到来源分支，再正常审阅。
- 保留人工修改的 PR 标题，以及正文生成标记之外的文字。不要删除标记。准备工作流运行期间，避免同时编辑正文；GitHub 的元数据编辑不是事务性编辑会话。
- 未合并便关闭 PR，会暂停该候选线。重新打开后手动运行 **Prepare release**，或等待下一次来源推送触发。
- 撤销显式版本覆盖、且没有需要发布的改动后，会关闭过时 PR 并写明原因，保留生成区之外的审阅说明。
- 存在草稿发布时，不再准备新候选。先完成或明确处理被中断的发布，绝不移动已存在的发布标签或版本。

恢复时手动运行 **Prepare release**，选择 `source=develop`。这是重试准备，不是再次确认发布的按钮。
失败会明确呈现，不暗中重试；不要以绕过分支保护或强推来解决它。

## 热修隔离与同步

经过审阅的 `hotfix/*` 合入 `main` 后，从 `main` 准备 `release/hotfix-next`，不携带尚未完成的开发工作。
手动恢复选择 `source=main`。两条候选线彼此独立。
再次准备普通发布之前，先通过受保护的 PR 流程，把稳定分支同步到 `develop`。
来源不包含当前 `main`，或候选记录的来源与当前来源历史分叉时，脚本会拒绝并要求审阅。
