# Native release artifacts

This describes the artifact format and build recipe, not an announcement that a
release has been published. [简体中文](release-artifacts.zh-CN.md) · [Release preparation](release-preparation.md)

## Contents and identity

The native targets are `x86_64-unknown-linux-gnu` and `aarch64-apple-darwin`.
Each `lattice-vX.Y.Z-TARGET.tar.gz` contains one identically named directory with:

- `lattice`, with executable mode `0755`;
- `LICENSE`, `NOTICE`, and `ASSET-ATTRIBUTION.md`;
- `THIRD-PARTY-LICENSES.html`, generated by cargo-about (it also includes Lattice's own license);
- `DEPENDENCIES.json`, a custom Cargo graph inventory, **not an SPDX/CycloneDX SBOM**;
- `SYSTEM-DEPENDENCIES.txt`, native shared-library inspection;
- `BUILD-INFO.json`, the build receipt.

The inventory can include build, development, and other-target dependencies; it
is not a claim that every entry was linked into this particular executable.
Unattributed local path dependencies are rejected rather than incorrectly assigned
to the root repository. Asset attribution remains separate from Cargo attribution.

The receipt records the source commit, version, target, preview flag, build-time
compiler, manifest/license-configuration digests, and the digests of packaged
files. It catches accidental mixing of builds and reports. **It is unsigned data,
not an independent proof of origin.** Official distribution additionally needs the
approved release, checksums, and workflow provenance; a version string or receipt
alone cannot turn a local package into an official release.

## Build a local preview

Use a clean checkout, including untracked source files, a native Rust toolchain,
Python 3.12, and the verified `cargo-about 0.9.2` executable on PATH. On macOS ARM64:

```sh
python3.12 scripts/build_release.py \
  --version "$(python3.12 -c 'import tomllib; print(tomllib.load(open("Cargo.toml", "rb"))["package"]["version"])')" \
  --commit "$(git rev-parse HEAD)" \
  --target aarch64-apple-darwin \
  --output target/release-preview \
  --preview
```

On Linux x86-64, select `x86_64-unknown-linux-gnu`; `ldd` and `readelf` must be
available. Cross-compiling is not this recipe's validation path. There is no
Windows or Intel macOS prebuilt target in this format.

The recipe builds with the lockfile, generates fresh attribution and dependency
reports, captures each producer's output digest, and rechecks the checkout and
compiler. Packaging refuses mismatched inputs, links, unexpected archive members,
invalid identity types, and inconsistent inventory references. The final archive
name appears only after validation succeeds; existing archives are not replaced.
Use a fresh output directory for a different build of the same version.

The archive is reopened and its extracted executable runs `--version` and
`--help` with a temporary home and a small explicit environment. This avoids
loading ordinary local settings; **it is not a filesystem or network sandbox**,
nor a paid-model or interactive-onboarding test. Distribution inspection can run
without executing either platform's binary in a privileged publication job.

Container ordering, ownership, modes, and timestamps are controlled. This does
not claim whole-binary reproducibility across compiler, SDK, or runner changes.
Local preview binaries exercise the release version format but are not releases.

## Distribution checks

`scripts/release_manifest.py` requires both platform archives for the same source
and phase. It produces `SHA256SUMS` and `release-manifest.json`, rejects unexpected
files, and refuses to replace different existing metadata. The workflow provenance
bundle is separate to avoid a self-referential checksum. Publication must verify
its repository, signing workflow, and source commit, not merely that some valid
signature exists. Publication integration and installation instructions are separate
from this local build recipe.
