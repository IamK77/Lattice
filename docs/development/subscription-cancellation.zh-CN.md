# 订阅取消：先记事实，再停止活动

## 生效点

`Unschedule` 与 `Unwatch` 取消的是订阅，不是撤回已经做过的事情。请求经过现有授权链，只有服务方的成功回执写入流水，订阅才算取消。生成回执本身没有停止副作用；后台线程在下一次检查时读取已经提交的事实并退出。即使进程在回执落账后、线程观察前退出，重启也不会复活已取消的订阅。

以下情况都不构成新协议下的取消：仅有请求、授权拒绝、工具错误、调用中断，以及还在部件发射缓冲区里的成功回执。取消成功仍只产生该调用的一份完成回执，不另造第二份工具结果。

已经越过停止检查点的唤醒可能继续完成，包括已经排队、但尚未落账或投递的唤醒。取消不保证线程在回执返回的一刻已经退出，不撤销已触发的模型轮次，也不回滚其工具操作。

## 服务方记录

成功回执沿用 `core.tool.exec.completed`，在 `result` 内增加 `cancellation: {"v": 1}`，并保留原来的数字 `timer` 或 `watch` 与 `note`。新增标记只说明回执采用这一提交语义，不改变核心事件信封。

每次恢复，服务方通过自己的 `state` 输出口记录 `timer.cancellation.activated` 或 `watch.cancellation.activated`，内容为 `v: 1` 与 `legacyThrough`。这是服务方拥有的事件类型；不需要给该输出口接回自身，也不要求核心理解取消。记录的来源确定当时的服务方身份。新回执必须来自这一身份，直接原因必须包含对应取消请求，且回执编号与请求参数相同。关卡转发仍沿用原有请求链。

后台线程共享按流水位置前进的读取视图，只处理新增记录。重启恢复使用同一份取消判定；派生检查点升级后从正本重建，不迁移或覆盖原始流水。数值编号接口不变，既有“先取消未来编号”的行为保留，未来编号也随恢复保存。

若取消记录或相关历史无法读取，恢复明确失败；运行中的线程停止本次后台活动并尝试记录带错误说明的唤醒，不能把读取失败当作“没有取消”。这种错误停止不冒充成功取消。

## 旧流水边界

旧实现的恢复逻辑见到取消请求就移除订阅，而实时停止又发生在成功回执落账之前。旧记录不能可靠证明当时线程是否已经停止；尤其不能凭现在缺少成功回执就推定旧订阅应该恢复。

首次升级因此记录固定的旧历史截止位置 `legacyThrough`：此前的记录保留旧恢复规则，包括其对拒绝请求的歧义；此后只认新协议成功回执。后续启动沿用原截止位置，不能把后来被拒绝或中断的请求纳入旧规则。首次激活若晚于已经入账的新请求，恢复会按明确截止位置重新派生，不把两者之间的请求误算为旧取消。

这是一条兼容边界，不是修复旧证据或保证旧历史判断正确。无需修改、删除或补造历史记录。

## 验证边界

回归检查覆盖定时器和文件监控的实际服务方、授权关卡拒绝与转发、回执仍在缓冲区时的实际停止视图、回执提交后的取消，以及跨次启动保持结果与旧历史边界。恢复检查另外覆盖当前订阅、未来编号、无回执或中断请求、冷恢复与检查点恢复、来源不符、记录损坏和旧新历史混合。

这些检查不依赖等待一段时间后“碰巧没有唤醒”来证明提交顺序，也不承诺操作系统线程强制终止、已开始动作回滚或进程崩溃时的磁盘硬件持久性。真实定时器与文件通知的既有集成检查继续验证正常触发、停止和恢复。
