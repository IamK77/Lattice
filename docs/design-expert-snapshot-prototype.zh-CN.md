# 自定义专家：授权与执行快照原型

这是 issue #45 的测试内架构验证，不是自定义专家功能的交付说明。生产代码、核心契约、工具入口和界面均未改变。

## 要回答的问题

用户批准的是一份具体内容，不能在真正开流时偷偷换成磁盘上的最新版。只在流水中记一个版本号也不够：子流必须实际使用获准内容。

原型把候选正文放进工具请求，由现有信任闸等待人的回答。请求获准并产生接受委派的事件后，测试中的延迟开流适配器沿因果链取回正文，再构造真正的子流装配。候选文件不再参与开流。

## 哪些是真的，哪些是合成的

真实执行链包括信任闸、授权回答、流水与因果引用、子代理部件、子流宿主、子流内核、模型请求、文件工具以及前台答复和后台唤醒。子流回答的跨流引用也经过核对。

以下部分仅用于测试：

- 候选格式和模型目录是合成数据；模型返回由脚本驱动，不连接供应商。
- 在测试装配中给 `ask` 增加了准入声明和候选参数。生产 `ask` 没有这些字段和行为。
- 内容摘要暂作模板名；这不是用户可见的命名方案，也没有实现动态发现。
- 延迟开流适配器仅存在于测试中，没有接入生产宿主。
- 能力对照借用现有 explorer / worker 装配，而非实现新的任意能力组合器。worker 的权限不止写文件。

## 留下的检查

定向运行：

```sh
cargo test --locked --test subagent snapshot_probe --no-fail-fast
```

五个用例分别检查：

1. 授权等待期间把 A 改为 B，批准原请求后仍执行 A。
2. 委派已经接受、宿主尚未开流时把 A 改为 B，仍执行 A。
3. 委派接受后删除候选文件，仍可执行已接受版本。
4. 明确批准 B，实际使用 B 的指令、脚本模型行为和可写装配，文件确实发生变化。
5. 拒绝请求只产生一个错误答复，没有被接受的委派，也没有写文件。

只读版本还检查了模型收到的工具清单不含 `Write`，伪造写调用没有改动文件且得到了中断结局。模型请求中的系统指令和工具清单通过正式文档引用读取函数还原，而不是把流水中的预览当正文。

同步依赖已有唤醒通道，没有用睡眠猜测任务完成时间；超时只用于终止失败的等待。

## 反向验证结果

曾故意把模板构造改为重新读取候选路径，同时保留正确的版本记账。两个内容变更用例实际收到 `ANSWER_B`，与预期 `ANSWER_A` 不符；删除用例因找不到候选文件而失败。另外两个对照用例仍通过。

恢复从流水正文构造后，五个用例全部通过。随后子代理、取消、信任闸和专家能力的相关测试全部通过，全目标静态检查也通过。

这说明测试能抓到“账上记的是 A，实际跑的是 B”，不只是检查一个版本字段。

## 结论与边界

现有授权、审计和开流机制足以承载这条最小链路，不需要给核心加入专家专用入口。候选、授权决定、执行快照是三个不同概念，但本原型不要求先建三套独立存储。

这不证明生产端已经能管理自定义专家，也不证明激活状态无需持久化。等待期间批准旧请求只授权其中的 A，绝不能据此把磁盘上的 B 标为已激活。

正式实现仍需补齐定义校验、项目与个人来源、修改冲突、授权内容展示、激活与撤销语义、真实模型目录解析、接受时冻结规范化执行配置、宿主接入和界面管理。模型凭证、重启后的恢复以及运行期依赖变化不在此次验证范围内；也没有证明跨二进制版本的可重复执行。

Issue #45 保持开放。此原型只是降低实现风险，不能代替功能验收。
